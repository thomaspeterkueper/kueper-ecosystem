# ECO-ARC-0027-2026-DE — Request, Task und Normierungsstelle

Status: accepted
Datum: 2026-07-26
Scope: systemweit
Betroffene Repositories: `kueper-ecosystem`, `kueper-knowledge-graph`, `kueper-archive-schema`, alle registrierten KUEPER-Repositories

## Kontext

V1–V7 (ECO-ARC-0019 bis 0026) haben Task-Lifecycle, Cross-Repo-Routing,
Research-/Canon-Validation-Loops und eine operative State Plane
(`ecosystem.*`-Schema in der `kueper-knowledge-graph`-Supabase-Instanz)
eingeführt. Das wirft drei bislang nicht formal geklärte Fragen auf, die über
einzelne Loop-Versionen hinausgehen und deshalb hier statt im
Ausführungscode entschieden werden:

1. Wo lebt die operative Wahrheit — GitHub-Dateien oder Datenbank?
2. Wie verhalten sich „Request" und „Task" zueinander, und was wird aus der
   in ECO-ARC-0013 für `kueper-archive-schema` ursprünglich vorgesehenen
   `requests`-Tabelle?
3. Wo verläuft die Grenze zwischen autonomer Ausführung und
   Owner-/Governance-Entscheidung?

## Entscheidung

### 1. `ecosystem.tasks` ist die operative Source of Truth, `external-tasks/*.md` ist Projektion

Ab sofort gilt:

```text
ecosystem.tasks (Supabase, State Plane)   = operative Wahrheit
external-tasks/*.md (GitHub)               = menschenlesbare Audit-Projektion
```

Das kehrt die bisherige Priorität um (External Tasks waren bislang selbst
die kanonische Quelle, ECO-ARC-0006). Diese Umkehr ist nur unter zwei
Bedingungen sicher, die hiermit verbindlich werden:

- **Synchronität ist Pflicht, nicht Kür.** Jede Zustandsänderung in
  `ecosystem.tasks`, die ein externes Repository betrifft, muss die
  zugehörige `.md`-Projektion innerhalb desselben Sweeps aktualisieren.
  Veraltete Projektionen sind ein Bug, kein akzeptabler Nebeneffekt.
- **Bei Widerspruch gewinnt die Datenbank.** Eine manuell bearbeitete
  `.md`-Datei ist ein Vorschlag/Kommentar, keine Korrektur der operativen
  Wahrheit, bis sie in `ecosystem.tasks` zurückgespiegelt wurde. Dies
  verhindert genau das Muster einer zweiten, konkurrierenden Wahrheit, das
  an anderer Stelle im Ökosystem (z. B. Impressum-Daten, ECO-ARC-0010/0016)
  bereits als Risiko identifiziert wurde.
- **Zugriff für Akteure ohne Service-Role-Key.** Jeder Mensch oder Agent
  ohne direkten Supabase-Zugriff (z. B. externe KI-Sessions, die nur
  GitHub sehen) muss sich auf die `.md`-Projektion verlassen können. Bleibt
  die Synchronität nicht gewahrt, ist diese Entscheidung faktisch außer
  Kraft, unabhängig davon, was hier steht.

### 2. Request und Task sind unterschiedliche Schichten, nicht konkurrierende Tabellen

```text
REQUEST  = Intent/Auftrag — was soll geklärt oder verändert werden
TASK     = ausführbare Arbeitseinheit — was das System konkret tut
```

Ein Request kann mehrere Tasks erzeugen. Die in `kueper-archive-schema`
(ECO-ARC-0013) ursprünglich vorgesehene, dort aber nie produktiv angelegte
`requests`-Tabelle wird **nicht verworfen**, sondern als `ecosystem.requests`
in der State Plane realisiert — oberhalb von `ecosystem.tasks`:

```text
ecosystem.requests   ← Intent / Auftrag (Governance-Ebene)
        │
        └── ecosystem.tasks   ← Execution (Worker-Ebene)
```

`kueper-archive-schema` bleibt Schema-/Archivprojekt für Dokumentarchive
(KUE/OTA) und wird **nicht** zum Host operativer Task-/Request-Infrastruktur.
ECO-ARC-0013 §„Umsetzungsplan" wird entsprechend präzisiert: die dort
skizzierte `requests`-Tabelle ist mit dieser Entscheidung nach
`ecosystem.requests` verlagert, nicht mehr Teil der Archive-Core-Migrationen.

### 3. Drei Entscheidungsebenen

```text
operational decision        → Agent entscheidet autonom
domain/canonical decision    → zuständiger Project Owner
creative/fundamentale        → Thomas
wissenschaftliche Entscheidung
```

Beispiele:

- „Diese Datei muss an die neue API angepasst werden." → autonom.
- „Diese Quelle widerspricht einer NOXIA-Annahme." → Agent erzeugt Request,
  entscheidet nicht selbst über Kanon-Änderung (bereits in ECO-ARC-0021/0022
  so festgelegt, hier bestätigt und generalisiert).
- „Soll NOXIA deshalb seinen Kanon ändern?" → NOXIA-Owner bzw. bei
  wesentlichem Kanon Thomas.
- „Ist ein Grundkonzept X überhaupt Bestandteil einer fundamentalen
  Annahme Y?" → keine autonome Systementscheidung, auch nicht Projekt-Owner
  allein — Thomas.

Die Normierungsstelle (dieses Governance-Layer, mit Thomas) definiert
Semantik, Grenzen und Konfliktauflösung. Sie definiert nicht jeden
Arbeitsschritt — das automatisiert der Loop darunter.

```text
                GOVERNANCE
            Normierungsstelle + Thomas
                    │
                    ▼
                 REQUEST
                    │
                    ▼
             KUEPER ECOSYSTEM
        Routing / Policy / Planning
                    │
                    ▼
                  TASKS
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
     NOXIA          KG          OTA ...
       │
       ▼
     RESULT ──────────────→ neue Requests
```

Der Loop ist Execution Infrastructure unter der Governance, keine zweite
Governance.

## Auswirkungen

- `ECO-ARC-0013` wird um einen Verweis ergänzt: die dort geplante
  `requests`-Tabelle ist nach `ecosystem.requests` verlagert.
- `docs/onboarding-template.md` sollte bei Gelegenheit den Hinweis erhalten,
  dass `external-tasks/open/` weiterhin die verbindliche
  Cross-Repo-Schnittstelle für alle ist, die keinen direkten
  Datenbankzugriff haben — nur die operative Wahrheit dahinter hat sich
  verschoben, nicht die Schnittstelle selbst.

## Nicht entschieden

- Konkretes Schema von `ecosystem.requests` (Felder, Beziehung zu
  `ecosystem.tasks` im Detail) — Umsetzungsdetail des Loops.
- Ob und wie das bestehende Dashboard (`app/`) künftig zusätzlich aus
  `ecosystem.tasks` liest statt nur aus `external-tasks/*.md` — separate
  Folgeentscheidung, falls gewünscht.
