# ECO-ARC-0024-2026-DE — Supabase Task Bus als operative State Plane

Status: accepted  
Datum: 2026-07-26  
Scope: systemweit  
Betroffene Repositories: `kueper-ecosystem`, alle registrierten Projekt-Repositories

## Kontext

V1–V5 haben Task-Lifecycle, Cross-Repo-Routing, Research, Canon-Validation und automatische Wiederaufnahme geparkter Tasks erfolgreich als GitHub-dateibasierte Loops definiert. Für dauerhaften autonomen Betrieb werden jedoch Abhängigkeiten, Leasing, Retry, Idempotenz, Worker-Ausfälle, Kosten-Telemetrie und unmittelbarer Event-Dispatch benötigt. GitHub-Dateien sind dafür als operative Queue zunehmend ungeeignet.

## Entscheidung

Das KUEPER Ecosystem erhält mit V6 eine dreischichtige Architektur:

1. **Control Plane** — `kueper-ecosystem`: Registry, Policies, Governance, Routingregeln, Budgets und Agentenprofile.
2. **State Plane** — Supabase/PostgreSQL: operative Source of Truth für Tasks, Abhängigkeiten, Runs, Leasing, Retry und Lifecycle-Events.
3. **Execution Plane** — austauschbare Worker: zunächst GitHub Actions plus Modellprovider; später weitere Runner möglich.

GitHub `external-tasks/` bleibt als auditierbare, menschenlesbare Projektion für relevante Cross-Repo-Vorgänge erhalten, ist aber nach vollständiger V6-Migration nicht mehr die operative Queue.

## Zustandsmodell

`pending → claimed → running → completed`

Zusätzliche Pfade:

- `running → pending` bei retry-fähigem Fehler;
- `running → failed` nach Ausschöpfung von `max_attempts`;
- `running → parked` bei interner Blockade oder Owner-Entscheidung;
- `parked → pending` nach erfolgreicher Reevaluation, sofern keine Owner-Entscheidung erforderlich ist;
- nicht-terminale Zustände können explizit nach `cancelled` wechseln.

## Leasing

Worker claimen Tasks atomar mit `FOR UPDATE SKIP LOCKED`. Jeder Claim erhält `lease_owner`, `lease_token` und `lease_expires_at`. Heartbeats verlängern die Lease. Abgelaufene Leases werden vom Watchdog zurückgesetzt oder nach Ausschöpfung der Versuche endgültig als `failed` markiert.

Damit blockiert ein abgestürzter Worker keine Aufgabe dauerhaft.

## Abhängigkeiten

`task_dependencies` bildet einen gerichteten azyklischen Graphen. Ein Task ist nur claimbar, wenn alle direkten Abhängigkeiten `completed` sind. Ein Trigger verhindert neu entstehende Zyklen.

## Idempotenz und Task-Ketten

`kueper_create_task()` verwaltet:

- `idempotency_key` gegen doppelte Producer-Events;
- `parent_task_id`;
- automatisch abgeleitete `root_task_id`;
- automatisch abgeleitete `depth`;
- optionale Abhängigkeiten.

Damit bleibt eine autonome Task-Kette vom Ursprung bis zum letzten Folgeauftrag nachvollziehbar.

## Sicherheit

Die operativen Tabellen verwenden Row Level Security. Zustandsverändernde RPCs werden `public`, `anon` und `authenticated` entzogen. Worker und Dispatcher greifen serverseitig über die Supabase Service Role zu. Service-Role-Secrets dürfen niemals in Browser, Projektcontent, Tasks oder Logs gelangen.

## Telemetrie

`task_runs` speichert pro Ausführungsversuch Worker, Modellprovider, Modell, Tokenverbrauch, geschätzte Kosten, Ergebnis und Fehler. `task_events` protokolliert Lifecycle-Übergänge.

## Nicht entschieden

Diese Entscheidung legt noch nicht fest:

- welchen Provider der Model Router pro Task auswählt;
- ob DeepSeek oder Codex Standard für Coding wird;
- die konkrete Database-Webhook-/Edge-Function-Implementierung;
- die endgültige Ably-Dashboard-Integration;
- die Migration bestehender `external-tasks` in Supabase.

Diese Punkte bauen auf der State Plane auf und werden separat implementiert.

## Folgeaufgaben

1. V6-Migration in der produktiven Supabase-Instanz anwenden und Smoke-Test ausführen.
2. GitHub Actions Worker an `kueper_claim_task()` und Lifecycle-RPCs anbinden.
3. Provider-/Model-Router ergänzen, DeepSeek als kostengünstigen Provider integrieren.
4. Event-Dispatcher über Database Webhook/Edge Function ergänzen.
5. Erst danach bestehende GitHub-Datei-Queue schrittweise zur Audit-Projektion degradieren.
