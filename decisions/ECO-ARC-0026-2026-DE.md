# ECO-ARC-0026-2026-DE — Provider Circuit Breaker für Billing- und Verfügbarkeitsfehler

Status: accepted  
Datum: 2026-07-26  
Scope: systemweit

## Kontext

Der erste reale V7-Pilot hat gezeigt, dass ein HTTP-402-Fehler (`Insufficient Balance`) technisch kein Taskfehler ist. Der Task wurde korrekt erneut auf `pending` gesetzt, verbrauchte dabei aber einen Retry-Versuch. Bei fortgesetztem Polling würde derselbe externe Providerfehler viele Tasks unnötig wiederholt treffen.

## Entscheidung

Providerbezogene Fehler werden von fachlichen Taskfehlern getrennt.

- HTTP 402 bzw. `Insufficient Balance` pausiert DeepSeek standardmäßig für sechs Stunden.
- HTTP 429/503 pausiert DeepSeek standardmäßig für 30 Minuten.
- Der betroffene Task wird über eine eigene RPC wieder auf `pending` gesetzt und verbraucht keinen Attempt.
- Während der Pause werden weitere DeepSeek-Tasks nicht ausgeführt, sondern auf später verschoben.
- Die Pause wird in `ecosystem.provider_state` gespeichert und ist damit workerübergreifend wirksam.
- Nach Ablauf von `paused_until` gilt der Provider bei der nächsten Verfügbarkeitsprüfung wieder als verfügbar.
- Normale Taskfehler bleiben Retry-/Failure-Fälle und erzeugen eine GitHub-Error-Annotation.
- Provider-Pausen erzeugen nur eine Warning-Annotation; sie sind kein Fehler des Tasks.

## Begründung

Billing, Rate Limits und Provider-Ausfälle liegen außerhalb der fachlichen Verantwortung eines Tasks. Sie dürfen weder Retry-Budgets verbrauchen noch eine Kaskade identischer Fehlversuche auslösen.

## Auswirkungen

Die State Plane unterscheidet nun Task-Lifecycle und Provider-Verfügbarkeit. Später kann der Model Router bei pausiertem Provider zusätzlich einen alternativen Provider wählen, statt nur zu warten.
