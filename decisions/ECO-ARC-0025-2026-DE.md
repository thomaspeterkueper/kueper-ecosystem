# ECO-ARC-0025-2026-DE — Execution Plane, Provider- und Kostenrouting

Status: accepted  
Datum: 2026-07-26  
Scope: systemweit

## Kontext

V6 stellt die operative State Plane bereit. V7 benötigt einen begrenzten Worker, der Tasks atomar claimt, Leasing respektiert, ein Modell auswählt, Arbeit ausführt und den Zustand ausschließlich über die State-Machine-RPCs zurückmeldet.

Für DeepSeek wurde vom Owner eine zeitabhängige Peak-Preisregel mit UTC-Fenstern 01:00–04:00 und 06:00–10:00 sowie Faktor 2,0 gemeldet. Da Providerpreise veränderlich sind, wird diese Annahme als Konfiguration und nicht als unveränderliche Programmlogik behandelt.

## Entscheidung

1. Der erste produktive Worker läuft als GitHub Action und verarbeitet pro Run höchstens eine konfigurierte kleine Anzahl Tasks.
2. Kein endloser Worker-Loop in GitHub Actions.
3. Jeder Task durchläuft `claim → route → start → execute → complete|fail|park`.
4. Lange Arbeit hält die Lease per Heartbeat am Leben.
5. Kostenempfindliche `low`/`medium`-Tasks dürfen während konfigurierter Peak-Fenster über `available_at` verschoben werden.
6. `high`/`critical` sowie Bugs, Build-Fehler, Security und Coding werden nicht allein aus Kostengründen verzögert.
7. DeepSeek ist V7-Standardprovider. Niedrige/mittlere Komplexität nutzt `deepseek-v4-flash`, hohe Komplexität `deepseek-v4-pro`, sofern kein Task-Override vorliegt.
8. Repository-Arbeit verwendet Claude Code als Agenten-Frontend mit dem dokumentierten DeepSeek-Anthropic-Endpunkt. Der Worker selbst kontrolliert Clone, Branch, Commit, Push und PR.
9. Nicht-Repository-Aufgaben können direkt über die DeepSeek Chat API verarbeitet werden.
10. Providerpreise und Peak-Fenster liegen in `config/provider-policy.json`.

## Sicherheitsgrenzen

- Secrets erscheinen nie in Prompt, Task-Payload, Commit oder Ergebnis.
- Der Agent darf nur das Ziel-Repository ändern.
- Ein optionales `base_sha` verhindert Ausführung auf veraltetem Repository-Stand.
- Owner-/Kreativentscheidungen werden geparkt, nicht geraten.
- Temporäre Blockaden können als normale `parked`-Tasks später wieder aufgenommen werden.
- Task-Zustände werden nur über die V6/V7-RPC-Fassade verändert.

## Betriebsmodell

Der GitHub-Worker läuft zunächst alle 15 Minuten plus manuell. Später soll ein Event-Dispatcher neue Tasks unmittelbar anstoßen; der periodische Lauf bleibt dann Watchdog/Fallback.

## Nicht entschieden

- dynamische Tages-/Projektbudgets;
- automatisches Benchmarking mehrerer Provider;
- Ably-Dashboard und Push-Status;
- vollständiger Cutover der alten GitHub-Datei-Queue.
